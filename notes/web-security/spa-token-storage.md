# SPA のトークンの置き場所

## 概要

SPA から API を呼ぶためのアクセストークンを、ブラウザのどこに置くべきかの整理。

結論:

- **できればブラウザにトークンを置かない**（BFF にして、ブラウザは HttpOnly クッキーだけを持つ）。構成は [SPA の認証構成パターン](spa-auth-architecture.md) を参照
- ブラウザに置くしかないなら、**メモリか sessionStorage。localStorage は避ける**
- ただし、置き場所を変えても XSS が起きれば取られる。**置き場所の工夫は被害を減らすところまで**で、本命は [XSS](xss.md) そのものを防ぐこと

## 脅威の整理

中心になる脅威は XSS。前提として次の 2 つを押さえる。

- **XSS を許すと、トークンをどこに置いても「ページが開いている間に、利用者として API を叩かれる」ことは防げない**。クッキー方式でも、攻撃スクリプトが `fetch` すればクッキーは自動で付く
- **置き場所で変わるのは「トークンを持ち出されるか」**。持ち出されると、利用者がタブを閉じた後でも、攻撃者の手元から、トークンが切れるまで使われる。リフレッシュトークンならさらに長く使われる

## 置き場所の比較

| 置き場所 | JS から読めるか | タブを閉じた後 | 評価 |
|---|---|---|---|
| localStorage | 読める | 残る | 最も持ち出されやすい。避ける |
| sessionStorage | 読める | 消える | MSAL.js の既定。妥協点 |
| メモリ（変数・Vue の `ref` など） | 直接は読みにくい | リロードで消える | `fetch` を書き換えられると盗まれる |
| HttpOnly クッキー（BFF） | 読めない | セッションの期限まで | トークン本体はサーバー側。CSRF 対策が要る |

## localStorage と sessionStorage の違い

**取られる条件（同じオリジンで攻撃者のスクリプトが動くこと）は同じ**。どちらも `getItem` で読める。
違うのは**トークンが置かれている期間と範囲**で、攻撃が起きたときにトークンがそこにある確率が変わる。

| | localStorage | sessionStorage |
|---|---|---|
| 消えるとき | 明示的に消すまで残る。ブラウザを再起動しても残る | タブを閉じると消える |
| 見える範囲 | 同じオリジンの全タブ | そのタブだけ |

| 状況 | localStorage | sessionStorage |
|---|---|---|
| ログイン中のタブで XSS が動く | 取られる | 取られる |
| 同じオリジンの別のタブで XSS が動く | 取られる | **取られない**（タブごとに分かれている） |
| ログアウトせずにタブを閉じ、後日 XSS のあるページを開く | **取られる**（前回のトークンが残っている） | 取られない（もう消えている） |
| 共有 PC で、閉じた後に別の人が使う | 残っている | 基本は消えている |
| 悪意のあるブラウザ拡張機能 | 取られる | 開いている間は取られる |

つまり、攻撃に対する強さが違うのではなく、**同じ攻撃に当たる機会の多さ**が違う。

sessionStorage でも油断できない点:

- **消えないことがある**。ブラウザの「前回開いていたタブを開く」や、閉じたタブの復元で、sessionStorage も復元されることがある
- **コピーされることがある**。「タブを複製」したときや、`window.open` で開いたタブには、元のタブの内容が引き継がれる
- **使い勝手が少し落ちる**。新しいタブではトークンが無い状態から始まる。ただ、IdP 側のログイン状態が残っていれば画面を出さずに取り直せるので、利用者が気づかないことが多い

## ブラウザで OAuth クライアントを動かす限りの限界

SPA 自身が OAuth クライアント（公開クライアント）になっている場合、XSS で入った攻撃者は**自分でトークン取得のフローを走らせて、新しいトークンを手に入れられる**（IETF の「OAuth 2.0 for Browser-Based Applications」が指摘している）。
そのため、ブラウザ内で置き場所をどう工夫しても、被害を減らすところまでしかできない。根本的に持ち出しを防ぐには、トークンをサーバー側に置く BFF にする。

## XSS 以外でトークンが漏れる経路

JS がトークンを持っていると、開発者からトークンが見えるので、うっかり漏れる経路が増える。モダンな技術に慣れていないエンジニアが多い環境では、XSS よりこちらのほうが現実的なこともある。

- `console.log` や、Application Insights などの監視ツールにトークンが記録される
- 調査のためにトークンをコピーして、チャットやチケットに貼る
- ブラウザの通信記録（HAR ファイル）を問い合わせに添付する。2023 年に Okta のサポート窓口で、HAR ファイルに含まれていたセッション情報が盗まれた事件があった

## 境界の防御があるときのリスクの見積もり

「端末の乗っ取りなら置き場所は関係ない」「IP 制限や WAF で守っている」という前提で、トークンの置き場所をどこまで気にすべきかの整理。

| 主張 | 評価 |
|---|---|
| PC が乗っ取られたら、置き場所は関係ない | **その通り**。情報窃取型のマルウェアは HttpOnly クッキーも含めて盗める。これは端末管理（EDR、Intune など）で守る領域 |
| トークンが盗まれる状況なら、それどころではない騒ぎになっている | **XSS には当てはまらない**。XSS は健全な PC で、アプリのバグや依存パッケージから起きる。騒ぎにならず、気づかないまま使われることが多い |
| Entra ID のサインインに IP 制限がある | **効くのはサインインとトークン更新のときだけ**。発行済みのアクセストークンを使うときに Entra ID は関与しない。API 側で制限していなければ、持ち出されたトークンは 1 時間前後どこからでも使える |
| APIM や Front Door で保護している | **API 側でも IP 制限を掛けているなら効果は大きい**。持ち出されたトークンを社外から使えなくなる。WAF だけなら、トークンを持った正規のリクエストとして通ってしまう |
| 盗まれても被害は少ない | **扱うデータ次第**。トークン 1 つで、そのフロントが呼べるすべての API を、その利用者の権限で使える。個人情報・人事・顧客情報を扱うなら小さくない |

まとめ:

- 確認すべきなのは「**API 側（APIM や Front Door）で、社外からのアクセスを IP で拒否しているか**」。拒否しているなら、トークンの持ち出しは低いリスクとして扱える
- ただし XSS の被害の本体は、トークンの持ち出しではなく、**その場での API 操作とデータの持ち出し**で、これはトークンをどこに置いても防げない（[XSS](xss.md) の「社内アプリでの経路」を参照）
- ゼロトラストの「どこかの防御は破られる前提で考える」観点では、IP 制限という境界の防御だけに頼らず、XSS の対策とトークンの扱いも一段ずつ重ねておくのが筋。ただし全部を同じ重さでやる必要はない

優先順位:

1. XSS を防ぐ（HTML を受け取らない部品、`vue/no-v-html`、CSP）
2. API 側の IP 制限を確認する
3. トークンをブラウザから無くす（BFF・中継）

すぐに中継に移行できない場合の当面の対策:

- localStorage から sessionStorage かメモリに変える（変更は小さい）
- リフレッシュトークンは保存しない
- トークンがログや監視ツールに出ていないかを確認する
